# KAJISHIFT 本番リリース判定基準（Release Criteria）

本ドキュメントは、KAJISHIFT を本番環境（バックエンド: **Railway**、フロントエンド: **Vercel**）へリリースする際の **Go / No-Go** の最終合格基準を定義する。  
技術スタックは **Node.js / Express / Prisma（PostgreSQL）** と **バニラ JS フロント** を前提とし、**Must-Have**（リリース不可）と **Should-Have**（計画付きで許容）を区別する。

---

## 1. はじめに（リリースの目的）

### 1.1 目的

- 依頼者・ワーカー・管理者が、**想定どおり安全に**サービスを利用できる状態であることを証明する。
- インフラ（Railway / Vercel）上で、**仕様書・OpenAPI・連携ドキュメント**と実挙動が一致していることを確認する。
- 個人情報・決済周り・リアルタイム通信における **セキュリティと可用性** の最低ラインを満たす。

### 1.2 適用範囲

| コンポーネント | 本番想定環境 | 参照ドキュメント（例） |
|----------------|-------------|------------------------|
| API / Socket.io / PDF | Railway | `README.md`、`docs/FRONTEND_INTEGRATION.md`、`docs/WORKER_UNAVAILABLE_SLOTS_API.md`、`docs/INSTALL_PDFKIT.md` |
| 静的フロント + PWA | Vercel | フロントリポジトリの `js/config.js`、Service Worker 設定 |
| 連携 | Railway ↔ Vercel | 本書 §3、`CORS_ORIGIN`、Socket 認証 |

### 1.3 用語

- **Must-Have**: 1 件でも未達なら **No-Go**（本番投入しない）。
- **Should-Have**: 未達でも **リスク明示と承認** があればリリース可能（ただし次スプリントで是正）。

## 2. 機能別合格基準（Must-Have / Should-Have）

### 2.1 バックエンド（Railway）

#### 2.1.1 DB 整合性 — `Booking` と `completedAt`、決済（Must-Have）

**背景（2026-05-01 以降のモデル）**  
Prisma の `Booking` に `completedAt`（DB 列 `completed_at`）が存在し、作業完了フローと一覧・詳細 API のレスポンスで一貫して扱われる。

| ID | 基準 | 検証方法（例） |
|----|------|----------------|
| B-DB-01 | ワーカーが `POST /api/bookings/:id/complete` を成功させたとき、同一トランザクション相当の更新として **`status === COMPLETED`** と **`completedAt` がサーバー時刻で埋まる**こと。 | DB 直接または API レスポンスで `completedAt` が非 null。 |
| B-DB-02 | `COMPLETED` 以外のステータスでは、ビジネスルール上 `completedAt` が不自然に残っていないこと（キャンセル等との矛盾なし）。 | 代表シナリオの回帰テスト。 |
| B-DB-03 | **決済との連動**: `Payment.status === COMPLETED` のレコードに対してのみ `GET /api/payments/:id/receipt`（PDF）が発行可能であること。未完了決済では 4xx 相当で拒否されること。 | 完了済み / 未完了の両方で API を叩く。 |
| B-DB-04 | 作業完了 API 自体は決済レコードを自動で `COMPLETED` にしない設計であれば、その旨を **製品仕様として文書化**し、画面上の期待（先払い・後払い等）と矛盾がないこと。 | プロダクト仕様との突合。 |

#### 2.1.2 PDF 生成（PDFKit + Noto Sans JP）（Must-Have）

| ID | 基準 | 検証方法（例） |
|----|------|----------------|
| B-PDF-01 | Railway デプロイ成果物に **`assets/fonts/NotoSansJP-Regular.otf`** および **`NotoSansJP-Bold.otf`** が含まれ、コンテナ起動時に存在すること。 | ビルドログ・本番シェルまたはヘルスチェック用スクリプトで確認。`docs/INSTALL_PDFKIT.md` に従う。 |
| B-PDF-02 | 本番で実際に `GET /api/payments/:id/receipt` を実行し、**日本語（依頼者名・住所・サービス名等）が豆腐化せず**読めること。 | 実 PDF をダウンロードして目視。 |
| B-PDF-03 | フォント未配置時は **明示的にエラー**となり、Helvetica 等への silent fallback で文字化けした PDF が配信されないこと。 | ステージングでフォントを一時除去した場合の挙動（開発時のみ）。 |

#### 2.1.3 セキュリティ — JWT とシークレット管理（Must-Have）

| ID | 基準 | 検証方法（例） |
|----|------|----------------|
| B-SEC-01 | `JWT_SECRET` は Railway の **Variables** にのみ設定され、リポジトリ・クライアント・ログに出力されていないこと。 | リポジトリ grep、Railway ダッシュボード。 |
| B-SEC-02 | 本番 `JWT_SECRET` は **32 文字以上の高エントロピー**（`src/config/env.js` の本番警告に従う）。 | 長さと生成手順の記録。 |
| B-SEC-03 | `DATABASE_URL` は Railway にのみ存在し、**公開バンドルに含まれない**こと。 | 同上。 |
| B-SEC-04 | 無効・改ざんトークン、期限切れトークンで保護 API が **401/403** で拒否されること。 | 自動または手動 API テスト。 |
| B-SEC-05 | ロールに応じた **authorize** が booking / payment / admin 系ルートで機能していること。 | 依頼者トークンでワーカー専用操作を試行等。 |

#### 2.1.4 API 仕様の一致（Must-Have）

| ID | 基準 | 検証方法（例） |
|----|------|----------------|
| B-API-01 | **`GET /api/bookings`** が `docs/FRONTEND_INTEGRATION.md` の記述どおり動作すること。特に次を満たすこと。 | 結合テストまたは手動。 |
| | • `available` は **WORKER のみ**有効。`true` / `1` / `yes`（大小・空白許容）、配列クエリは先頭正規化。 | ワーカー・依頼者の両方で確認。 |
| | • `startDate` / `endDate` が `YYYY-MM-DD` のとき **UTC 日境界**で `scheduledDate` と整合。 | タイムゾーン跨ぎの 1 ケース以上。 |
| B-API-02 | **`/api/workers/me/unavailable-slots`** 系（GET / POST / PUT sync / DELETE）が `docs/WORKER_UNAVAILABLE_SLOTS_API.md` および `docs/openapi-worker-unavailable-slots.yaml` と一致すること。 | Postman / OpenAPI 検証。 |
| B-API-03 | 認証必須エンドポイントでトークンなしのとき **401** 等、仕様どおりのエラー形式であること。 | サンプル複数ルート。 |

**Should-Have**

| ID | 基準 |
|----|------|
| B-API-S01 | Swagger UI があれば本番 URL と同一バージョンでホストされ、上記エンドポイントが一覧可能であること。 |

### 2.2 フロントエンド（Vercel / バニラ JS）

※フロントのソースは別リポジトリの場合があるが、**本番リリース判定はフロントを含めて一括**で行う。

#### 2.2.1 UX / UI（Must-Have）

| ID | 基準 | 検証方法（例） |
|----|------|----------------|
| F-UX-01 | モバイル表示で **`#fixedActionBar`**（下部固定アクションバー）が **主要ブラウザでタップ可能**であり、スクロール時に本文を過度に隠さない、またはスクロールで到達可能なこと。 | iOS Safari / Android Chrome の実機または DevTools。 |
| F-UX-02 | バニラ JS による画面遷移が **二重送信や壊れた history** なく、主要フロー（ログイン → 予約 → 完了）が通ること。 | E2E またはチェックリスト。 |

#### 2.2.2 PWA / Service Worker（Must-Have）

| ID | 基準 | 検証方法（例） |
|----|------|----------------|
| F-PWA-01 | 本番オリジンで Service Worker が **登録・稼働**し、DevTools Application タブでエラーがないこと。 | Vercel 本番 URL。 |
| F-PWA-02 | キャッシュ戦略が **API レスポンスを誤って長期キャッシュして古いデータを表示しない**設計であること（またはそのリスクが許容され文書化されていること）。 | ネットワークパネルで `API_BASE_URL` 呼び出しの Cache-Control を確認。 |

#### 2.2.3 ロール別アクセス（Must-Have）

| ID | 基準 | 検証方法（例） |
|----|------|----------------|
| F-RBAC-01 | **依頼者（CUSTOMER）** セッションでワーカー専用・管理者専用 URL にアクセスしたとき、**フロントでガード**され、または API が **403/401** で拒否され、機密データが表示されないこと。 | URL 直打ちテスト。 |
| F-RBAC-02 | **ワーカー（WORKER）** と **管理者（ADMIN）** についても同様に、権限外画面へ到達できないこと。 | 各ロールで矩形成。 |

#### 2.2.4 環境設定（Must-Have）

| ID | 基準 | 検証方法（例） |
|----|------|----------------|
| F-ENV-01 | `js/config.js`（または同等の単一設定源）の **`API_BASE_URL`** が **Railway 本番 API の HTTPS オリジン**を向いていること。 | 本番ビルドのファイル内容またはランタイムで `console` / ネットワークタブ確認。 |
| F-ENV-02 | **`SOCKET_SERVER_URL`**（または Socket.io クライアントが接続する URL）が **本番 Socket エンドポイント**（通常は API と同一オリジンまたはドキュメント化されたサブドメイン）を向いていること。 | Socket 接続成功・イベント受信。 |

**Should-Have**

| ID | 基準 |
|----|------|
| F-ENV-S01 | ステージング用の `config` 切替が誤って本番に混入していないこと（Vercel Preview の環境変数と Production の分離）。 |

### 2.3 連携・リアルタイム（Socket.io）（Must-Have）

| ID | 基準 | 検証方法（例） |
|----|------|----------------|
| S-RT-01 | 本番フロントから本番 Socket.io に **接続・再接続**でき、認証後に通知または予約ステータス更新が **実用的な遅延（目安: 数秒以内）**で UI に反映されること。 | 2 ブラウザまたはユーザーで予約更新。 |
| S-RT-02 | サーバー側 Socket CORS が **`CORS_ORIGIN` と整合**し、不正オリジンからの接続が拒否されること。 | `src/config/socket.js` の挙動に沿って確認。 |
| S-CORS-01 | HTTP API の **`CORS_ORIGIN`** が、本番フロントのオリジン（既定例: **`https://kajishift-frontend.vercel.app`**）に **適切に絞られている**こと。ワイルドカード本番運用や `*` は禁止。 | Railway Variables と `src/index.js` の origin 設定の突合。 |
| S-CORS-02 | プレビュー用 URL が必要な場合は **明示的にカンマ区切りで列挙**され、不要なドメインが含まれていないこと。 | 変数の値をレビュー。 |

## 3. 非機能要件（パフォーマンス、セキュリティ、インフラ）

### 3.1 パフォーマンス（Should-Have 中心）

| 区分 | 基準 |
|------|------|
| Must | 本番で主要ページの **LCP が著しく悪化していない**（フロント側で計測可能なら数秒以内を目安）。 |
| Must | `GET /api/bookings` 等の一覧が、通常データ量で **タイムアウトしない**（Railway の無料枠等の制限は別途文書化）。 |
| Should | PostgreSQL に適切なインデックスが張られ、N+1 が顕在化していないこと（Prisma の `include` 設計のレビュー）。 |

### 3.2 セキュリティ（Must-Have の再掲と追加）

- **HTTPS のみ**（Vercel / Railway の既定 TLS）。
- **依存パッケージ**の既知脆弱性: リリース前に `npm audit`（または組織ポリシーに従うスキャン）を実施し、**Critical は是正または例外承認**。
- **レート制限**（導入済みの場合）は本番で有効であること。

### 3.3 インフラ（Must-Have）

| ID | 基準 |
|----|------|
| I-01 | Railway で **本番ブランチ・自動デプロイ**が正しく指されていること。 |
| I-02 | **マイグレーション**（`prisma migrate deploy`）が本番 DB に適用済みであること。 |
| I-03 | ヘルスチェックまたは最低限の **プロセス生存監視**があること。 |

## 4. 法的・運用チェック

### 4.1 法的・コンプライアンス（Must-Have）

| ID | 基準 |
|----|------|
| L-01 | **利用規約・プライバシーポリシー**がフロントから到達可能な URL で表示されること。 |

### 4.2 運用・バックアップ（Must-Have / Should-Have）

| ID | 区分 | 基準 |
|----|------|------|
| O-01 | Must | Railway に紐づく PostgreSQL の **バックアップ方針**（プロバイダの自動バックアップ有無、リストア手順のリンク）がドキュメント化されていること。 |
| O-02 | Should | インシデント時の連絡先（オンコール）とロールバック手順が 1 ページにまとまっていること。 |
| O-03 | Must | 本番 **ログにパスワード・JWT・DATABASE_URL を出さない**こと。 |

## 5. 最終判定フロー（Go / No-Go）

### 5.1 判定手順

1. **§2 の Must-Have** をチェックリスト化し、QA が証跡（スクショ、HTTP ログ、PDF ファイル、DB クエリ結果）を添付する。  
2. **§3・§4** の Must を満たすことをインフラ・リードが確認する。  
3. Should-Have の未達は「残債一覧」に起票し、プロダクトオーナーが許容するか判断する。  
4. 下記 **署名欄** にて Go / No-Go を記録する。

### 5.2 Go / No-Go の定義

| 判定 | 条件 |
|------|------|
| **Go** | §2〜§4 の **Must-Have がすべて達成**され、重大な未修正バグがない。 |
| **No-Go** | Must-Have のいずれかが未達、またはセキュリティ・データ損失の重大リスクが残存。 |
| **条件付き Go** | Should-Only の未達のみで、承認済みの残債と期限が付記されている（稀。通常は Go にまとめる）。 |
