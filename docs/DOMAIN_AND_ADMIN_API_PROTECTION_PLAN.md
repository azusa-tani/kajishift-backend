# Cloudflare・ドメイン公開・管理API保護方針

最終更新: 2026-07-08  
確認者: `KAJISHIFT運用担当`

このドキュメントは方針整理用であり、Cloudflare、DNS、独自ドメイン、Vercelドメイン設定、Railway、Stripe、DB、Webhook、deployの実操作は行わない。

個人名、メールアドレス、電話番号、住所、問い合わせ本文、審査回答本文、問い合わせID、userId風の値、workerId、bookingId、予約ID、submissionId、APIキー、Secret、DB接続文字列、決済情報の実値は記録しない。

## 1. 目的

2026年7月7日にA案「本番決済なし限定公開」として公開済みのKAJISHIFTについて、次に進める必要があるCloudflare、独自ドメイン、管理API保護の方針を整理する。

A案中は、問い合わせ、事前登録、β利用希望、サービス内容閲覧、サイト確認モニターからのフィードバック受付に公開範囲を限定する。正式予約、本番決済、本番カード登録、家事代行の実働、worker受注・辞退・作業完了、管理画面更新系操作は開始しない。

## 2. 現在の公開URLと独自ドメインの関係

現時点の公開確認は、VercelのProduction Aliasを基準に行う。

- 現在の利用者向け公開URL: `https://kajishift-frontend.vercel.app`
- Backend APIはFrontend設定経由で本番Backendに接続する。
- 独自ドメインは、A案中に勝手に切り替えない。
- Cloudflare、DNS、Vercel Domains、リダイレクト、SSL/TLS設定は、実操作前にGo/No-Go判断を行う。

独自ドメイン公開後は、利用者向けの主要導線を独自ドメインへ統一する。ただし、切り替え前にA案の誤認防止文言、本番決済未開始、正式予約未開始、カード登録未開始が引き続き分かることを確認する。

## 3. Cloudflareを使う場合の目的

Cloudflareを使う場合の主な目的は以下。

- DNS管理を一元化する。
- SSL/TLSを適切に終端し、HTTPSで安全に公開する。
- `www` あり / なしのリダイレクト方針を統一する。
- 最低限のセキュリティ設定を行う。
- 将来的にWAF、Bot対策、Rate Limiting、キャッシュ制御を検討できる状態にする。

A案では、Cloudflareの導入目的を方針整理と手順整理にとどめ、実際のDNS切り替えや設定変更は行わない。

## 4. A案中に実施してよい作業

A案中に実施してよいのは、実環境を変更しない準備作業に限定する。

- Cloudflare利用目的の整理
- DNS設計案の整理
- 独自ドメイン公開手順の整理
- `www` あり / なしの正規URL方針案の整理
- SSL/TLS設定方針案の整理
- 変更前チェックリスト作成
- Go/No-Go判断項目の整理
- ロールバック方針の整理
- docsへの方針記録

## 5. A案中に勝手に実施しない作業

以下は、A案中に明示的な合意なく実施しない。

- DNS切り替え
- Cloudflare設定変更
- Cloudflare Nameserver切り替え
- Vercelドメイン追加
- Vercel Production Domain変更
- リダイレクト設定変更
- SSL/TLS設定変更
- Cache Rules、Page Rules、WAF、Rate Limitingの有効化または変更
- Railway、Vercel、Stripe、DB、Webhook、外部監視サービスの設定変更
- deploy、再deploy、commit、push

## 6. 独自ドメイン公開前に確認すべき項目

独自ドメイン公開前に、少なくとも以下を確認する。

- 正規URLを `www` あり / なしのどちらにするか決める。
- 非正規URLから正規URLへのリダイレクト方針を決める。
- Vercel側で必要なドメイン設定手順を整理する。
- Cloudflare側のDNSレコード案を整理する。
- SSL/TLSモードの方針を決める。
- HSTSの有効化可否を判断する。初回公開では慎重に扱う。
- FrontendからBackend APIへのCORS設定が、独自ドメイン公開後のOriginと整合することを確認する。
- OAuth、メールリンク、通知、問い合わせ返信など、URLを含む設定の影響範囲を確認する。
- Service Workerやキャッシュの影響を確認する。
- A案の誤認防止文言が独自ドメインでも表示されることを確認する。
- 予約作成、予約確定、決済、カード登録、worker受注・辞退・作業完了が開始済みに見えないことを確認する。
- 切り戻し手順を事前に決める。

## 7. 実操作前のGo/No-Go判断項目

実操作前に以下を満たす場合のみGo候補とする。

- 実施日時、担当者、影響範囲、切り戻し手順が明確である。
- DNS TTL、反映時間、確認方法が整理されている。
- Vercel、Cloudflare、Backend CORSの設定変更順序が整理されている。
- 独自ドメイン公開後もA案の公開範囲に限定されることを確認済み。
- 正式予約、本番決済、本番カード登録、本番課金導線が開始されないことを確認済み。
- 管理画面更新系操作を行わないことを確認済み。
- 変更前後に確認するURLと画面が決まっている。
- No-Go時の戻し先が `https://kajishift-frontend.vercel.app` 基準で明確である。

No-Go候補:

- CORS設定変更が未整理。
- SSL/TLSモードが未確定。
- リダイレクトループのリスクが未確認。
- VercelとCloudflareの設定責任範囲が不明。
- A案の誤認防止表示を独自ドメインで確認する計画がない。
- 切り戻し手順がない。

## 8. `/api/admin/*` の保護方針

`/api/admin/*` は、B案移行前または正式公開前に追加保護を必須とする。

方針:

- 管理者認証を必須にする。
- 管理者ロール確認を全admin APIで一貫して実施する。
- 更新系、削除系、承認/却下系、合格/不合格系、CSV/Excel出力系は特に強い保護対象とする。
- 必要に応じてIP制限、VPN、Cloudflare Access、Basic認証、管理画面専用ドメインなどを検討する。
- 監査ログ、操作ログ、アラート通知を検討する。
- CSRF、CORS、Rate Limit、セッション管理、JWT失効、権限昇格リスクを確認する。

## 9. 管理画面アクセス制限

正式運用前に、管理画面へのアクセス制限を検討する。

候補:

- Cloudflare Accessで管理画面を保護する。
- 管理画面URLを利用者導線から分離する。
- 管理者だけがアクセスできるネットワーク制限を検討する。
- 管理者ログイン後も、API側で必ず権限チェックする。
- フロント側非表示だけに依存しない。

A案中は管理画面を読み取り確認に限定し、更新・削除・承認/却下などは行わない。

## 10. 管理者MFA/2FA

B案移行前または正式公開前に、管理者アカウントのMFA/2FAを必須化する方針を検討する。

確認観点:

- 管理者ログインにMFA/2FAを必須化できるか。
- 初期設定、再設定、紛失時復旧の運用を用意できるか。
- MFA未設定管理者を制限できるか。
- MFA設定状態を管理者一覧や監査対象として確認できるか。

## 11. 管理者ログイン失敗時のアカウントロック

管理者ログインは、一般利用者より強い保護を検討する。

方針:

- 一定回数の連続失敗で一時ロックする。
- ロック解除手順を運用で定義する。
- ロック発生時に運用通知する。
- IP、User-Agent、時刻などの監査情報を実値を公開せず内部で確認できるようにする。
- docsにはアカウント名、メールアドレス、IPなどの実値を記録しない。

## 12. 管理画面更新系操作の扱い

A案中は、管理画面更新系操作を行わない。

更新系操作の例:

- 承認
- 却下
- 削除
- 合格
- 不合格
- 停止
- 有効化
- アサイン
- 対応開始
- ステータス変更
- CSV / Excel出力
- 決済、返金、報酬精算、キャンセル料管理に関する操作

これらを正式運用する前に、権限、監査ログ、誤操作防止、確認ダイアログ、通知、ロールバック方針を整理する。

## 13. 承認・却下・削除・合格・不合格を正式運用する前の条件

正式運用前に以下を満たすこと。

- 対象操作の権限設計が明確である。
- 取り消し可否、取り消し手順、影響範囲が整理されている。
- 操作ログが残る。
- 操作前確認ダイアログや二重確認がある。
- 重要操作は必要に応じて複数人確認にする。
- 操作結果の通知先と文言が整理されている。
- 個人情報や審査回答本文を不要に露出しない。
- 誤操作時の一次対応手順がある。
- Stagingまたは検証環境で確認済み。

## 14. A案中に許可する確認範囲

A案中に許可する確認は読み取り限定。

許可:

- 管理画面の一覧や詳細の表示確認
- 件数や状態の抽象確認
- Slack通知の到達確認
- A案の誤認防止文言確認
- Console / Networkの読み取り確認

禁止:

- 登録送信
- 予約作成
- 予約確定
- 決済
- カード登録
- 承諾
- 辞退
- 作業完了
- 管理画面の更新・削除・承認/却下
- CSV / Excel出力
- DB、Stripe、Railway、Cloudflare、Vercel、Webhook、外部サービスの操作

docsには個人情報、ID実値、問い合わせ本文、審査回答本文、決済情報、Secret類を残さない。

## 15. B案移行前の必須タスク

B案移行前または正式公開前に、少なくとも以下を必須タスクとして扱う。

- 管理画面アクセス制限
- 管理者MFA/2FA
- 管理者ログイン失敗時のアカウントロック
- `/api/admin/*` の追加保護
- 管理画面更新系操作の権限・監査ログ・誤操作防止整理
- 脆弱性診断またはペネトレーションテスト証跡
- Stripe本番Webhook確認
- Stripe本番決済の成功/失敗/反映確認
- worker向け仕事詳細・承諾導線を正式公開する場合の、個人情報を返さない公開案件専用API設計
- 独自ドメイン公開を行う場合のCloudflare / DNS / Vercel / CORS確認

## 16. 追加で確認すべきリスク

- 独自ドメイン公開後のCORS不整合。
- CloudflareとVercelのSSL/TLS設定不整合。
- `www` あり / なしのリダイレクトループ。
- Service Workerやブラウザキャッシュによる古い表示。
- 管理画面URLの露出。
- 管理APIの認証・認可漏れ。
- 管理者アカウント乗っ取り。
- CSV / Excel出力による個人情報持ち出し。
- 承認・却下・削除・合格・不合格の誤操作。
- 監査ログ不足により、操作経緯を追えないリスク。
- A案中にもかかわらず、正式予約・決済・実働が開始済みに見える表現が残るリスク。
